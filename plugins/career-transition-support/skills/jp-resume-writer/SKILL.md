# 職務経歴書作成 (ITエンジニア向け)

日本のIT転職市場における職務経歴書を、markdown形式で作成・添削するためのskill
出力はWordに貼り付けてPDF化する運用を想定し、Excelは使わない

## 前提

日本国内の中途採用では、米国のATS (採用管理システム) のような機械的キーワードスクリーニングより、
転職エージェントや人事担当者が直接目を通す比率が高い
したがってフォント指定や用紙マージンといった機械可読性の細部より、
人間が読んだときの分かりやすさと実績の具体性を優先する

## 標準構成 (この順序で作成する)

1. **日付・氏名** — 上部に「職務経歴書」の見出し、作成日と氏名
2. **職務要約** — 3〜4行、「実務年数・得意領域・最大の実績」を一文でまとめる
3. **職務経歴** — 会社名・在籍期間・雇用形態、**逆編年体形式** (直近の経歴から古い順)
4. **開発経歴** — プロジェクトごとにプロジェクト概要、役割・チーム構成、担当業務・成果、技術的課題と解決策、使用技術を記載
5. **スキルレベル** — カテゴリ別 (言語/フレームワーク/DB/クラウド・インフラ/CI・CD/テスト/ツール) に経験年数と実務使用の有無を記載
6. **最終学歴** — 学校名は正式名称、学部・学科、卒業年月まで記載
7. **保有資格** — 取得年月と正式名称を省略しない
8. **自己PR** — 「何ができるか」「どう貢献できるか」を簡潔に

逆編年体形式を使う理由は、採用担当者が最も知りたいのは「今この人が何をできるか」であり、
直近のプロジェクトと使用技術が即戦力かどうかの判断に直結するため

分量目安はA4 1〜2枚相当、開発経歴が多い場合は2枚まで許容する

## 開発経歴の書き方

各プロジェクトは次の見出しで構成する

- プロジェクト概要 (何を、誰向けに、どんな規模で)
- 役割・チーム構成
- 主な成果・実績
- 技術的課題と解決策
- 使用技術 (表形式、分野別)

## 実績の書き方の型

対象・規模 + 行動 + 技術内容 + 成果/インパクト、の順で一文にまとめる

弱い例 「AWS環境の運用を担当」
強い例 「500アカウント規模のAWSマルチアカウント基盤の運用を担当し、Python (Pandas) によるコスト分析を実施、自チームで月間400万円のコスト削減を達成」

避けるべき表現

- 「〜に従事」「〜を担当」で終わる、成果が書かれていない文
- 主語が曖昧で、自分が何をしたか分からない文
- 一文が長すぎて、行動と成果の対応関係が読み取れない文

## 数値化の手法

実績はできる限り数値で示す。次の6カテゴリで数値化できないか確認する

1. 金額 (コスト削減額、予算規模、売上貢献)
2. 時間 (作業時間短縮、リードタイム短縮)
3. 割合 (改善率、削減率、効率化率)
4. 規模・量 (アカウント数、ユーザー数、チーム人数、リクエスト数)
5. 品質 (エラー率、可用性、SLA達成度)
6. 頻度 (日次/月次の処理件数)

### 数値が不明な場合の推定

正確な数値が分からない場合も、以下の方法で概算を示す。ただし推定であることが分かるよう
「約」「〜以上」「〜規模」を必ず添える。実態より過大に盛らない

- 保守的推定 低めに見積もる (例 100時間削減の確証がなければ「約70時間以上削減」)
- 範囲推定 「X〜Y」の形で示す (例 「8〜12名のチーム」)
- 最小値提示 「X以上」の形で示す (例 「100件以上」)
- 活動比率からの逆算 全体の数値が分かる場合、担当割合から計算する (例 全社1000件中2割担当 = 約200件)
- 頻度からの逆算 週あたりの件数から年間換算する (例 週5件×50週 = 約250件/年)

## ITエンジニア向け技術カテゴリ

スキルレベルの記載は次のカテゴリで整理する。書けるカテゴリのみで構わない

| カテゴリ | 例 |
|---|---|
| 言語 | Java、Python、TypeScript、Go |
| フレームワーク | Spring Boot、React、FastAPI |
| データベース | PostgreSQL、MySQL、DynamoDB |
| クラウド・インフラ | AWS、Azure、Kubernetes、Terraform |
| CI・CD | GitHub Actions、CodePipeline、Jenkins |
| テスト | Playwright、JUnit、Moto |
| ツール | Git、Jira、Docker |

各項目に、実務での使用有無 (「実務経験あり」「個人開発のみ」など) を添えると採用担当者が判断しやすい
経験年数は「3年」のように年数で示すか、「2022年〜現在」のように期間で示す

SES業界などで「スキルシート」と呼ぶ場合、本skillの8項目構成ではなく技術一覧のみの別フォーマットを指すことがある
その場合は必要な項目のみを抜き出して作成する

## 作業の進め方

1. 新規作成か既存ファイルの添削かが不明な場合、以下をもとに`AskUserQuestion`ツールを呼び出してユーザに確認する

   ```
   questions:
     - question: 職務経歴書の作成方法を教えてください
       header: 作成方法
       multiSelect: false
       options:
         - label: 新規作成
           description: ヒアリングから職歴・実績を聞き取って作成する
         - label: 既存ファイルの添削
           description: 既存の職務経歴書ファイルを読み込んで添削する
   ```

   新規作成の場合はユーザーの職歴・実績をヒアリングし、添削の場合は既存ファイルを読み込む
2. 各プロジェクトの実績を「実績の書き方の型」に沿って書き起こす
3. 数値化できる箇所を洗い出す。実績の数値が不明な場合、以下をもとに`AskUserQuestion`ツールを呼び出してユーザに確認する

   ```
   questions:
     - question: この実績の数値が不明です。どの推定手法で示しますか
       header: 数値の推定手法
       multiSelect: false
       options:
         - label: 保守的推定
           description: 低めに見積もる (例 「約70時間以上削減」)
         - label: 範囲推定
           description: 「X〜Y」の形で示す (例 「8〜12名のチーム」)
         - label: 最小値提示
           description: 「X以上」の形で示す (例 「100件以上」)
   ```

4. 標準構成の8項目に沿って全体をmarkdownで組み立てる
5. 弱い表現がないか見直し、成果が書かれていない文を修正する

## このskillで扱わないもの

- フォント指定、用紙マージンなど印刷レイアウトの細部 (Word側で調整するため)
- ATSキーワードマッチ率の算出 (求人票とのマッチ度分析は jp-job-posting-analyzer を使う)
- 個人開発プロジェクトの詳細なケーススタディ (jp-portfolio-case-study を使う)
