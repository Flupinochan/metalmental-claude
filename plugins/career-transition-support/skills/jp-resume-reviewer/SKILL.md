# 職務経歴書レビュー

既存の職務経歴書を、中途採用で重視される観点に基づいてレビューするためのskill

## レビュー観点

### 1. 簡潔性・深掘り前提の書き方

採用担当者が書類に最初に目を通す時間は短いため、結論と数値を先に示し、手段の詳細や経緯は面接での深掘りに委ねる
業務内容を列挙するだけでなく、課題から結果までを一連の流れとして簡潔にまとめる

#### 弱い例

"求人サイトサービスのAPI新規・保守開発を行いました。主に開発、詳細設計、実装、テスト、リリース作業に従事"
→ 担当工程の列挙に留まり、どんな課題をどう解決したか、結果どうなったかが書かれていない

#### 強い例

"コードが散乱し開発環境の構築に時間がかかっていた状態から、Docker Composeで環境を統一し1コマンドで立ち上げられるように改善"
→ 課題、手段、結果が一文で読み取れる。工程の詳細は面接で聞かれる前提で削る

### 2. ベクトルが外、会社や他者に向いているか

個人の成果だけで終わらせず、資産として残ったか、他者や組織の生産性が上がったかまで書く

#### 弱い例

"開発環境をDocker Composeで統一した"
→ 自分が作った、で終わっているため、誰がどう使えるようになったか分からない

#### 強い例

"コードが散乱し環境構築が属人化していた状態から、Docker Composeで環境を統一し1コマンドで立ち上げられるようにしたことで、新規参画メンバーも当日から開発に着手できる状態にした"
→ 恩恵を受ける対象を明示しているため、個人の成果が組織の資産になったことが伝わる

他の資産化パターンの例

"手順書やガイドラインの整備によって、属人化していた作業を誰でも再現できる状態にした"
"社内勉強会や知見の共有によって、チーム全体のスキルや生産性を引き上げた"

### 3. 数値とプロセスの具体性、STARフレームワーク

結果だけでなく、課題から行動に至る経緯を、数値結果とセットで示す
STARはSituation、Task、Action、Resultの頭文字で、状況と課題から行動、結果までを一連で書く型

#### 弱い例

"顧客と良い関係を築いた"
→ 何をして、どの程度の成果が出たのかが分からない抽象的な表現

#### 強い例

"既存顧客への定期フォローを月1回から週1回に増やし、問い合わせ対応の初動を平均2日から半日に短縮したことで、顧客接点を20%増やした"
→ 行動の変化と数値結果の両方が書かれているため、再現性のある成果として伝わる

数値が不明な場合の推定例

正確な数値が分からない場合も、推定であることが伝わる表現を使う
"対応件数が週10件程度から週3件程度に減少" のように、程度や約を添えて保守的に推定する
実態より過大に盛らず、面接で数値の根拠を説明できる範囲に留める

### 4. 募集要件・応募企業との整合性

応募職種と無関係な技能を並べるより、募集内容に沿った経験を優先して見せる
同じ実績でも、応募先が重視する軸に応じて職務要約の先頭に置く実績を入れ替える

例、バックエンド採用向け

大規模データ処理やAPI設計の実績を職務要約の先頭に配置する

例、UI/UX寄りの採用向け

画面パフォーマンス改善やユーザー体験に関する実績を職務要約の先頭に配置する

採用担当者は冒頭の職務要約と応募職種との距離感を早い段階で見るため、応募先ごとに見せる順序を調整する価値がある

### 5. 書類全体の一貫性

職務要約、職務経歴、自己PRが同じ実績を異なる粒度で説明しているか確認する
キャリアの継続性、転職理由や空白期間の説明に不自然さがないか確認する

#### 弱い例

職務要約に"マネジメント経験あり"と書いているが、職務経歴本文にはメンバーとしての担当業務しか書かれていない
→ 職務要約と職務経歴の内容が矛盾しているため、どちらが正しいか読み手が判断できない

#### 強い例

職務要約の"4名チームのリード経験"を、職務経歴側で"チーム4名のタスク配分と進行管理を担当"という具体的記述で裏付ける
→ 職務要約と職務経歴が同じ実績を異なる粒度で説明しているため一貫性が保たれる

### 6. 体裁・フォーマットの正確さ

レイアウト、分量、他の提出書類との整合性を確認する

チェック例

分量がA4用紙2〜4枚程度に収まっているか、趣味やボランティアなど職務と無関係な情報で水増しされていないか確認する
逆編年体式など標準的な形式から外れたレイアウトになっていないか確認する
履歴書など他の提出書類と、入退社年月や資格取得日などの日付が矛盾していないか確認する
敬語と常体が混在するなど、文体が統一されていない箇所がないか確認する
"〜を担当" "〜に従事" で終わる、成果が書かれていない文が残っていないか確認する
取引先の具体名やプロジェクトの機密情報など、守秘義務に反する記載がないか確認する

### 7. 技術職特有の専門性と鮮度

技術スキルはバージョンや開発規模、実務経験年数とセットで書くことで実務レベルが伝わる
継続的な学習習慣、資格取得、技術発信、OSS貢献など、スキルの鮮度を示す情報も評価対象になる

#### 弱い例

"Javaの開発経験があります"
→ バージョンや開発規模、実務経験年数が書かれていないため、スキルレベルが判断できない

#### 強い例

"Java11を用いた基幹システムのリプレース案件に3年間従事、チーム6名でバックエンドAPIを担当"
→ バージョン、プロジェクト規模、チーム人数、担当範囲が明確なため実務レベルが伝わる

コードレビューやメンタリングなど、技術力以外でチームに貢献した経験も鮮度や協調性を示す材料になる

### 8. 生成AIらしさの排除

定型文や抽象的な表現の多用は、AIで一括生成したような印象を与え、他の候補者との差別化にならない
整いすぎた文体で人間らしい揺らぎがない場合、文末表現や接続詞が機械的に単調な場合、結論から理由列挙・まとめという構成が毎回同じ型で繰り返される場合も生成AIらしさにつながる

#### 弱い例

"チームワークを活かし、プロジェクトを成功に導きました"
→ 誰にでも当てはまる抽象的な表現で、固有の経験が伝わらない定型文

#### 強い例

"5名体制のプロジェクトで、仕様の認識齟齬によるリリース遅延が続いていた課題に対し、週次の仕様レビュー会を新設して齟齬を事前に解消した"
→ 固有の人数、課題、行動が書かれているため、定型文ではなく実体験として伝わる

書いた内容は面接で自分の言葉で説明できる範囲に留め、具体的なプロジェクト名や人数、予算規模などの固有情報を落とさないようにする

## レビューの進め方

1. 職務要約を読み、実務年数・得意領域・最大の実績が簡潔に伝わるか確認する
2. 各実績を上記8観点でチェックし、該当しない箇所を指摘する
3. 弱い例に該当する文を見つけたら、強い例の型に沿って改善案を提示する
4. 応募先が分かっている場合は観点4に基づき、提示順序の変更を提案する
5. 指摘は観点ごとに箇条書きで、該当箇所を見出し名または行の冒頭数文字で明示する
